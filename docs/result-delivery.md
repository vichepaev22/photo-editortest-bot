# CR-018: повторная доставка результата, 11.10.2026

Статус требования: принято прямым указанием владельца «внедри 1» из обзора Context7. Каноническое требование: PRD.md, R05. До изменения оба пользовательских пути всегда отправляли FSInputFile. Область изменения: первая доставка результата и /result/кнопка собственного результата; административная доставка, рассылки, подписки, кредиты и генерация не изменяются.

## Контракт

- Успешный send_document возвращает Message; непустой строковый document.file_id сохраняется в отдельной добавочной SQLite-таблице. Ключ включает числовой bot.id, user_id, job_id; result path дополнительно сверяется. Токен бота не сохраняется.
- Перед любой выдачей проверяются generated/delivered, владелец, согласие, существующий локальный файл и его прежний TTL 24 часа. Кэш не продлевает доступ после удаления или истечения TTL.
- Повторная выдача того же результата этим ботом отправляет строку file_id. Другой bot ID загружает локальный файл и сохраняет собственный ID. Кэш переживает новый Store/процесс.
- Только явный Bad Request о неправильном/истёкшем file_id разрешает забыть ID и один раз загрузить локальный файл. Другие Bad Request и сетевые ошибки не вызывают повторной отправки.
- TelegramRetryAfter сохраняет retry_at = текущий момент + retry_after. До этого срока документ не отправляется; после срока только явный запрос результата повторяет доставку. Автоматический outbox не добавляется.
- Неопределённый сетевой исход не повторяется автоматически. Сохранённый результат остаётся доступен в истории; paid Image API, reservations и списания в этом слое отсутствуют.
- Только успешная доставка переводит generated в delivered и разрешает существующую очистку сообщений шагов.

## Приёмка и проверки

| ID | Наблюдаемый результат |
|---|---|
| RD1 | Первый upload возвращает file_id; после нового Store повтор отправляет строку, а не InputFile |
| RD2 | Другой bot.id делает собственный upload; прежний ID не используется |
| RD3 | Чужой user/job, отсутствие согласия, удалённый или старый файл дают ноль send_document, включая прогретый кэш |
| RD4 | Wrong file identifier даёт один fallback upload и новый ID; произвольный Bad Request даёт одну попытку без fallback |
| RD5 | 429 сохраняет дедлайн; ранний запрос не отправляет; поздний явный запрос доставляет прежний результат, provider.calls и баланс не меняются |
| RD6 | Network timeout даёт одну попытку и generated, без повторного Image API и без очистки шагов |
| RD7 | /result и callback собственного результата используют один и тот же кэш; captions/filename PNG/JPEG сохраняются |

Проверки выполняются офлайн с настоящими aiogram Message/Document и SQLite в pytest tmp_path. Реальные Telegram-сообщения, polling, Image-вызовы и production deployment не входят в эту проверку.

## Документация и совместимость

Установлено aiogram 3.31.0 (requirements.lock и импорт runtime). Context7 resolve/query выполнены ведущим агентом в текущем запросе: `/aiogram/aiogram`, темы повторного upload через file_id и TelegramRetryAfter.retry_after. В окружении этого субагента сервер временно отсутствовал; результаты текущих запросов переданы ведущим агентом. Сигнатуры TelegramBadRequest/TelegramRetryAfter и bot.id дополнительно сверены по установленной библиотеке. Источники: [upload_file](https://docs.aiogram.dev/en/latest/api/upload_file.html), [send_document](https://docs.aiogram.dev/en/latest/api/methods/send_document.html), [exceptions](https://docs.aiogram.dev/en/latest/dispatcher/errors.html).

OpenAI SDK 2.54.0 и модель/quality/size сохраняются. Сравнение моделей — будущий отдельный эксперимент с бюджетом и критериями качества; Context7 не доказывает качество модели на фотографиях пользователя.
